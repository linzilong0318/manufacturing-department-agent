# 制造部数据洞察助手（DTX 断路器项目）

> **一句话**：一个给制造部用的数据洞察 skill——业务人员问一句大白话（产量、能耗、产值、气量、设备盘点），直接拿到可信结论，背后的时区口径、单位换算、采集断供甄别全部自动处理。

---

## 1. 它解决什么问题

制造部的数据躺在 TDengine 里，但查一个数要提需求、等排期、反复确认口径。数据背后还有一堆"看不见的坑"：

- 同一指标在不同粒度下单位不同（如产量，5 分钟粒度是**台数**，按日汇总却是**极数**）；
- 数据时间线有两套（北京时间业务日 vs UTC 实时时间戳），差 8 小时；
- Daily 汇总表的 ts 是 UTC 16:00 对齐，代表**次日**北京时间全天；
- 67 线的三相电表在独立的 CT 表组里，只查主表会漏掉整条产线；
- 空结果可能是"当天确实无产出"，也可能是"采集断了"，判断错了会误导决策。

**这个 skill 把全部复杂性封装在后台，业务人员只需要开口问。**

## 2. 目标用户

| 用户 | 角色 | 诉求 |
|---|---|---|
| 业务人员 | 制造部车间主管 / 计划员 / 能源员 / 工程师 | 问一句大白话，直接拿到可信结论 |
| 数据团队 | 制造部数据维护者 | 维护背景知识、沉淀案例，越用越准 |

## 4. 使用方式

- **入口**：加载 `tdengine-query` skill 后，直接按 SKILL.md 的执行流程走；
- **查询链路**：业务问题 → 案例库三维度匹配 → 背景知识映射（model-map）→ SQL 执行 → 多重验证 → 业务解读；
- **工具选择**：优先 MCP 只读工具（select/show/describe）；不可用时走 REST 备选（`http://10.120.7.99:6041/rest/sql`）；多表 UNION ALL 查询用 `run_sql_file.py` 程序化提交；
- **产出要求**：输出规范见 SKILL.md Step 0——结论先行、单位明确、附数据完好性说明，不直接抛 SQL。

## 5. 质量承诺（为什么数据可信）

1. **零篡改**：展示的每个数字与工具返回值完全一致，绝不手工算合计；多源加总一律在 SQL 层完成；
2. **空结果不误导**：先验证 `first(ts)/last(ts)` 区分「业务无产出」和「数据采集中断」，结论附数据完好性说明；
3. **口径透明**：单位永远说清楚（台、极、元、kWh 等），用户说"产量"未指定口径时台数和极数都给出；
4. **时区统一**：全文件统一 Daily 表句式 `ts=X 日 16:00 UTC = BJT (X+1) 日全天`，杜绝混用。

## 6. 边界与限制

- **只读边界**：只查数据，绝不改动生产数据；
- **覆盖范围**：只覆盖已建模的数据域（产量/产值/能耗/气量/设备盘点），未建模指标需先完成建模；
- **数据质量**：底层采集中断时如实告知可查范围，不编造、不补救；
- **静态表**：累计类表（Total*New）与单耗指标表时间戳停在 2017-12-31，不可用于当前分析，必须按区间 SUM 实测。

## 附录：技术概览（给技术读者）

- **数据源**：TDengine，数据库 `dtx_385318105131300357`，MCP 只读工具访问（SELECT only）；
- **表模式**：单元级 `quota_...@<模型>@<指标>`；设备级 `quota_sub_<实例ID>@<指标>`；所有表名必须用反引号包围；
- **时区**：北京时间 T 日 = UTC (T-1) 16:00 ~ T 16:00，区间左闭右开；
- **易错拼写**：`project_DayilyModelEnergy`（Dayily 是库内真实拼写，勿"纠正"）；
- **质量机制**：`verify_cases.py` 校验案例库编号、`sql-hygiene.md` 的程序化 SQL 构建、采集三层状态甄别。
