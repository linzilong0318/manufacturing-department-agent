## Lesson 7: 查询返回空时，先验证数据时间范围，且不要把临时数据状态写死进文档 (2026-08-07)

**问题：** 用户问某型号"昨天的产量"，查询返回空。第一次处理时直接下结论，还把"全库数据截止某日期"写进了 lessons —— 这是错误做法：数据截止是**临时状态**，采集恢复后该结论立即过时，会变成误导性信息。

**正确做法：**
1. 查询返回空时，用 `SELECT last(ts)` 确认该表数据时间范围，判断是"该日期确实无数据"还是"数据截止/缺失"
2. 向用户如实说明数据范围，不要编造数字
3. **只把方法论写进 lessons（如"先验证时间范围"），不要把具体数据状态（截止日期、某型号某时段无产量）写成固定事实**——那是易变信息，属于查询结果，不属于经验

**教训：** lessons 记录的是可复用的判断方法；数据快照属于一次性的查询结果，写进去会在数据更新后变成错误 lesson。

## Lesson 1: ProductTypeAgg ID → 型号名称 应查文档而非 EquipmentModel (2026-08-05)

**问题：** 查询 M09 线 6/1 数据时，从 `project_5minsM09ModelYield` 查到了 ProductTypeAgg instance_uid=`2042842697696993280`（产量1200台，3600极）。为了找这个型号的名称，我去查了 EquipmentModel 体系的 PEM 表和 maktx 表——绕了一大圈都没匹配上，因为 ProductTypeAgg 和 EquipmentModel 是**完全独立的 ID 命名空间**。

**正确做法：** `dtx-model-map.md` 文档中 ProductTypeAgg 实例列表已经列出了所有97个型号的 ID → 名称映射。直接搜索该文件就能找到 `NXB-63 3P D20 | 2042842697696993280`。

**教训：** 查到 ProductTypeAgg 的 instance_uid 后，优先去 `dtx-model-map.md` 反查型号名，不要在 TDengine 里绕弯路。

**⚠️ 重复犯错记录 (2026-08-05)：M04产线查询中再次犯同样错误。**
- 场景：查到 NXB-63 3P D32 (2042843330912477184) 有产量，先去了数据库查 maktx/PEM 表，没匹配到才放弃
- 根因：查ID后第一反应是"去数据库找"，没有切换为"去业务知识库查映射"
- **强制流程：** 拿到 ProductTypeAgg 的 instance_uid 后，**第一步**就是 grep `dtx-model-map.md`，不要先去数据库绕圈。这是必须执行的操作顺序，不是选项。

## Lesson 2: 一次性定义时区边界，避免前后矛盾 (2026-08-05)

**问题：** 查47号线6/1~6/4产量增长率时：
- 第一次 SQL 用 `BJ 6/1 = UTC 5/31 16:00 ~ 6/1 16:00` → 得到39600
- 后续 SQL 换了不同边界 → 得到不同数字
- 然后开始混淆不同边界下的结果
- 最终告诉用户的数字是错的

**正确做法：** 一次性定义好所有天的 UTC 边界（如 BJ 6/1 = UTC 5/31 16:00 ~ 6/1 16:00），所有 SQL 都用同样的边界逻辑，最好放一条 SQL 里用 UNION ALL 一次性查完。

**教训：** 算增长率（环比/定基）时，一天的数据错了所有百分比都会错。提交前先核对 raw timestamps 确认边界是否正确。

## Lesson 3:查询为天为单位的数据时， 优先用 Daily 汇总表，不要自己从5min数据汇总 (2026-08-05)

**问题：** 查47号线6/1~6/4产量时，我没有先查 `project_Daily47ModelYield` 这个每日汇总表，而是直接从 `project_5mins47ModelYield`（5min粒度）手工SUM汇总。

- Daily 表有6/1~6/3的数据（6/1=21600, 6/2=39600, 6/3=39600）且与5min汇总一致
- 6/4 Daily 表无记录（数据截止了），这时才需要用5min补充

**正确做法：**
1. 先查 `project_Daily{线}ModelYield` —— 又快又准
2. Daily 表缺的天再用 `project_5mins{线}ModelYield` 补充

**教训：** 不要绕过 Daily 表直接去手工汇总5min数据。Daily 表不完整时才用5min补充。

## Lesson 4: "产量"=？ 用户没说清楚时，台数和极数都返回 (2026-08-05)

**问题：** 用户问产量增长率，我回答了"极数"并按极数算的，但用户纠正"产量应该是台数"。

**规则：** 当用户问"产量"而没有明确说是台数还是极数时，**两个都返回**。

**关键区分：**

| 概念 | 单位 | 对应字段 |
|---|---|---|
| 产量(台数) | **台** | `5mins{线}ModelYield`, `YIELD` |
| 极数 | **极** | `{线}ExtremeNumber`, `Daily{线}ModelYield` |

**⚠️ 特别注意 `ModelYield` 前缀在不同粒度表中的单位不同：**
- `project_5mins{线}ModelYield` = **台数**（统计类）
- `project_Daily{线}ModelYield` = **极数**（计算类）

所以查每日产量(台)时：
- ❌ 直接用 Daily 表的值 → 对于2P/3P/4P型号会差2~4倍
- ✅ 用 `project_5mins{线}ModelYield` 按 UTC 边界SUM
- ✅ 或用 Daily 值 ÷ 每台极数（前提是知道型号的极数）

**换算关系：** 极数 = 台数 × 单台极数
- 1P→1极/台, 2P→2极/台, 3P→3极/台, 4P→4极/台

**教训：** 用户没说清楚时，**台数和极数都展示**，让用户自己选。

## Lesson 5: 不允许擅自修改 dtx-model-map.md (2026-08-05)

**问题：** 之前 session 中我修改了 `/opt/data/skills/data-science/tdengine-query/dtx-model-map.md` 来补充新的型号/实例信息。

**纠正：** `dtx-model-map.md` 是**业务知识库**，由制造部/文档团队维护，Agent 不能擅自修改。

**正确做法：** 业务知识更新由用户在飞书/wiki 端维护，Agent 只读使用。经验和教训放在 `lessons.md`（本文件）。

**⚠️ 授权边界补充 (2026-08-12)：** 经用户明确授权的**结构整理**（如合并速查表、调整章节位置、增删说明文字）可以修改 dtx-model-map.md；但**业务数据内容**（97型号列表、实例ID、表名、单位口径等）的增改仍属文档团队职责，Agent 不得擅自添加/修改/删除。区分标准：结构 vs 业务数据。

## Lesson 6: 永远不要向用户展示原始UID，必须翻译为型号名称 (2026-08-06)

**问题：** 用户问"67号产线目前生产的最多的设备是哪台"，我查到了 ProductTypeAgg instance_uid 为 `2042841124683407360`，虽然在 dtx-model-map.md 中已经映射为 NXB-63 2P C32，但回答时直接贴了UID，用户追问"为什么给我返回的是UID"。

然后用户又问第二个型号，我回答"查不到具体型号"——但实际上 dtx-model-map.md 中 ProductTypeAgg 实例列表里就有 `2042840421838282752 → NXB-63 2P C20`，我没有去查。

**这是 Lesson 1 在第三次重复犯错！** Lesson 1 已经记录了同一个问题（ProductTypeAgg ID 应查文档而非数据库），但这次更严重——文档里有现成映射，我连查都没查。

**根因分析：**
1. 拿到 instance_uid 后默认反应是"我查到了→直接输出"，而不是"我查到了→去文档翻译→再输出"
2. 对用户的"设备"一词理解偏差——用户问的是"设备型号"，我理解成了"设备工位/单元"
3. 没有形成映射的肌肉记忆，dxt-model-map.md 已经反复证明是 ProductTypeAgg ID 翻译的权威来源

**强制规则：**
- **输出要求：** 对于"哪个设备/型号产量最多"类问题，永远输出 `型号名称（产量XX台）`，而不是 `instance_uid（产量XX台）`
- **当我说"查不到"时，检查是否真的查了所有可能来源：** dtx-model-map.md 的 ProductTypeAgg 列表、maktx 表、PEM 表。不要只查一个来源就下结论
