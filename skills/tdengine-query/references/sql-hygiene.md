# SQL 卫生：程序化构造 + 以工具绝对值为准 (2026-08-18)

本文件记录查询 TDengine 时两个反复出现的可复用技术，避免再次踩坑。

## 技术1：手写 SQL 时间戳/表名会系统性转录出错——改用程序生成

### 现象
同一会话内连续 5+ 次手写 SQL 出错：
- 时间戳 `2026-07-31 16:00:00` 被污染成 `2026-07-022 16:00:00`、`... 9416:00:00`、`... 944:00:00`（"16"变成"9416/944"）
- 产线表名后缀 `M06`/`49`/`67` 被插入脏字符：`project_DailyM064ModelYield`、`Daily49Model7Yield`、`Daily674ModelYield`

全部是手工拼接长 SQL（14 条产线 UNION ALL + 重复时间戳）时，注意力涣散导致插入/删减字符，且错位肉眼难辨，报错 `[0x127] Invalid timestamp format` 前不自我暴露。

### 正确做法
1. **时间戳、表名后缀先定义为变量**，用 Python 拼接出完整 UNION ALL SQL：
   ```python
   start_utc = "2026-07-31 16:00:00"; end_utc = "2026-08-01 16:00:00"
   lines = ["M01","M02","M03","M06","M09","M012","49","50","67"]  # 14 条线后缀
   sql = "\nUNION ALL\n".join(
       f"SELECT '{l}' AS line, SUM(val) FROM `...project_Daily{l}ModelYield` "
       f"WHERE ts >= '{start_utc}' AND ts < '{end_utc}'" for l in lines)
   # 断言校验每一行
   assert all(f"@project_Daily{l}ModelYield` WHERE ts >= '{start_utc}'" in sql for l in lines)
   ```
2. 生成的完整 SQL 贴进 MCP query 工具执行。
3. 报错 `[0x127]` 时第一反应是"SQL 拼错了"——重新用程序生成，不要在错误原稿上猜改（原地修补会再错一次）。
4. 多行重复结构：肉眼逐行核对后缀+边界，或用断言程序化校验后再提交。

### 适用范围
任何多次出现相同时间戳、或 UNION ALL 多行相同结构的查询（14 条产线、多气表、多月对比等）。单一短查询可手写，重复结构一律程序生成。

## 技术2：复核合计时禁止手写中间值——以 SQL SUM 绝对值为唯一事实来源

### 现象
查询 M03 线 8/1~8/8 能耗，SQL 已返回合计 `1410.3`。为"复核"，试图逐日重加，却凭空写出 `9481.06`、`87920.9`、`236.889` 等**非工具返回的臆造值**，自找迷惑。

### 根因
拿到工具返回的逐日明细后，不再是"引用原始输出"，而是"凭印象重数/重写"数值——制造出比原始数据更不可靠的中间数。违反零篡改铁律（SKILL.md 规则0：展示数据必须与工具返回值完全一致）。

### 正确做法
1. **以 SQL 层 `SUM(val)` 绝对值为最终数字**，工具的聚合返回天然零篡改。
2. 需复核时：**重新查询**拿精确值，或把工具**原始返回值**原样喂进程序累加；绝不手抄/记忆重写数值。
3. 展示的逐日表中每个数字必须与 MCP 原始行一致；不一致就重新查询，不改数。
4. 一旦意识到自己在"重数/补值"，立即停手，回到工具原始输出。

### 适用范围
一切展示合计/逐日明细给用户的查询。零篡改适用于所有数字，不只限于本技能。
