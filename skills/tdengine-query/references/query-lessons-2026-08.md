# 累计口径与大结果集交付（2026-08 会话补充）

> 可复用判断方法论（非数据快照）。设备计数见 `device-inventory.md`、产线耗电见 `daily-energy-query.md`；本文件补充跨主题教训。
> Lesson 规则：只记录判断方法，不写数据快照（截止日期、具体数值易变）。

## 教训 B：总表 vs 分表的"累计读数"口径不同，不可相加/直接比较

**问题：** 用户问"某产线总表和分表的总耗电量"，分别取主三相电表累计值（`EP` 有功总电能）和 13 台单元微断累计值（`project_TotalEnergyConsumption`），结果**分表合计远大于主表**——不是数据错误，是两者累计起点/计量口径不同。**不可相加，也不可用分表之和校验主表。**

**正确做法：**
1. 主电表累计读数用 `EP`（有功总电能）；单元微断累计读数用 `project_TotalEnergyConsumption`。
2. 二者累计起点不同（分表多为设备投运起独立累计，主表 EP 是本安装周期累计），**量级可能差数倍**。
3. 要**同一时间段**对比"总表 vs 分表"，必须用**日/区间消耗口径**（主表 `public_dailyEnergyConsumption` / 分表 `project_DailyEnergyConsumption`）按同一 UTC 边界 SUM，而不是累计读数。
4. 对用户明确区分两个口径：**累计表底数（累计读数）** vs **某区间消耗量（日消耗求和）**。气表同理：累计底数 `project_TotalUsageNm3`（表底数，期初期末之差才是期间消耗）vs 日消耗 `project_dailyUsageNm3` 按区间 SUM。逐日求和值与累计表底数差是不同概念，勿混为一谈。

**教训：** 涉及"总表/分表、累计/消耗"时先确认口径，别把一个不可比的结果当结论展示；用户没说明时可两口径都讲并注明各自含义。

## 教训 D：用电数据异常甄别——先定位巨值/0值再报口径

**问题：** 用户查"上个月耗电"等汇总时，个别日期会出现计量跳变巨值（如 M03/67/M06 某日突现 25万~28万 kWh，正常仅 200~400），直接 SUM 会把整月结果虚高到 25万级，误导排名。

**正确做法（可复用 3 步）：**
1. **SUM 前先查是否存在巨值**：对区间内 `val > 5000`（正常单日约 200~3000）的记录单独 `SELECT line, ts, val` 定位异常日。
2. **异常日通常与全厂总表巨值同日**（如 7/13、7/14 全厂总表 25万/56万），可交叉验证为同一批电表故障，非真实生产。
3. **剔除异常后再报真实合计**：**按产线只剔除它自己出现巨值的那一天**（各线异常日可能不同：如 67线=M06线都在 7/13，而 M03 在 7/12），不要把所有异常日对全部产线统一排除——否则会对无异常产线误删真实耗电（实测：把 7/12 和 7/13 都对所有线排除时，M03 从正确值 7217.7 被误算成 9415.77）。可用 `ts NOT IN ('<该线异常日>')` 逐线指定；能容忍时用 `AND val < 10000` 兜底，但要清楚它同样会误删个别正常超量日。标注异常日期/数值，让用户知情。异常值只剔除汇报，不修库（只读红线）。

**另：0 耗电天数可识别停产 vs 数据故障。** 全厂周日/周末停产，正常产线 0 耗电约 7~11 天（6/1~8/8 全期）；明显超出的线（如 M09=37、M03=24、M05=18）多为电表断流/长期停线，非正常停机，直接影响月度统计准确性，应提示用户核查。判断时按产线 `GROUP BY COUNT(*) WHERE val=0`，与正常停产基线对比。

## 教训 E：采集状态三分类——"记录停更" vs "心跳仍在但数值冻结" vs "真无产出" (2026-08-31)

**问题：** 用户问某日各产线产量。Daily 表止于 8/8（无 8/9、8/10 汇总行），但设备级累计表 `FINISH_YIELD` 的时间戳**仍每分钟更新到 8/10 14:30**——初看像"数据还活着"。查逐分钟明细才发现：累计值自 8/8 00:00 起**冻结在同一数字不变**，只有时间戳在跳动（占位心跳）。该日查询全表 val=0，但那属"采集无新数据"而非"产线停产"。

**三类状态要区分（判断采集健康度/是否可查时）：**
| 现象 | 含义 | 是否可回答业务 |
|---|---|---|
| 记录完全停更（last(ts) 停在旧日期，无新行） | 采集链路断（link dead） | 不可查，如实告知 |
| **时间戳持续更新、但累计值冻结在同一数字不变** | **链路心跳仍在，但无新数据写入（数值冻结）** | **不可查，不可当停产；拉逐分钟明细看值是否变** |
| last(ts) 到当天 + 目标日有非零行 | 链路在职，可正常查 | 可查 |

**正确做法：**
1. 判断"数据是否存活"不能只看 last(ts) 或表是否有新行——对**累计量/测点类表**（如设备级累计产量、电表累计值），要取两个时间点的值**对比是否变化**：`SELECT ts, val ... ORDER BY ts LIMIT 若干`，看末段 val 是否仍是同一数字。
2. 时间戳更新的新行里 val 若恒等于前值 → 数值冻结、无新数据，即采集中断的变体；给用户结论时要明确这是"采集断流"，不是"产线停产"。不能编造后段产量。
3. 多汇总口径（Daily 汇总、5min 分线/全局、设备级累计）交叉印证：本例三种口径全部停在同一点之后，共同收敛于同一结论，证据才足。
4. 补充验证：`SELECT last(ts) FROM {明细表} WHERE val > 0` 拿到最后**非零值**时刻，比 last(ts) 更能代表"最后真实数据"。

**教训：** 时间戳存活 ≠ 数据存活。报表链路"心跳还在、数值冻结"是比"记录彻底停更"更隐蔽的断流形态，必须对比值是否在变，不能只看行是否更新。

## 教训 C："全部记录"大结果集 → 主动导 CSV，别只贴终端表格

**问题：** 用户查"所有记录的耗电量"（数十上百天），天然是大表，直接贴 markdown 表格在飞书里又长又难用。

**正确做法：** 大量行（数十行以上）的明细查询，主动用 execute_code 把结果写成本地 CSV（utf-8-sig 利于 Excel 打开中文），用 `MEDIA:<绝对路径>` 发给用户，正文只放关键汇总 + 数据要点。导出前做异常值甄别（如累计跳变巨值），给"含异常合计"与"剔除异常后合计"，说明数据质量（规则0：异常值先重查验证，标注而非直接删改数字）。

## 教训 F：EP 累计值重置归零——LAST(val)=0 时别直接判"用电为0"

**问题：** 用户查各产线总用电量排行。查14线 EP `LAST(val)`，发现某产线最新值=0，但 `first(ts)` 显示数据已从数月前采集至今。若直接判该线无用电，会漏掉它曾经积累的电量。

**正确做法（可复用流程）：**
1. 在全部产线 EP 循环查 `LAST(val)` 时，对 val=0 的记录单独标记。
2. 对该线执行 `SELECT first(ts), last(ts) FROM 该线@EP`，确认数据时间跨度。
3. 若跨度>数天且全是旧数据→电表被重置：`SELECT MAX(val) FROM 该线@EP WHERE ts < {第一个0值时间}`，取重置前最大值作为"该线历史累计最高用电"。
4. 展示时标注：该线电表曾重置归零，重置前历史累计最高约 X kWh（表底数重置，非该线累计用电为0）。

**鉴别特征：** EP 是有功总电能，正常情况下应**单调非递减**（只会增长或持平，不会下降）。一旦最新值 < 历史任一时点值，即发生重置。LAST(val)=0 + 历史有正数 = 明确重置信号。

**教训：** 对累计读数类指标（EP、FINISH_YIELD、ZYGDNEN），最新值为 0 不等于是"该线无用电/无产出"，必须先排查重置或清零事件。
